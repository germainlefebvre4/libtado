## Context

See proposal.md - Why. Relevant current state:
- `libtado/api.py` talks to the live Tado API via `requests`.
- `tests/api/utils.py` wraps each `get_*`/`set_*` call for exactly one live account topology (`zones[0]`, `zones[1]`, a specific `dayType`, etc.).
- CI secrets (`TADO_USERNAME`, `TADO_PASSWORD_B64`, `TADO_CLIENT_SECRET`, `TADO_BRIDGE_AUTHKEY`, `TADO_CREDENTIALS_FILE`) already exist for `check_json_schemas.yml` and `template_test.yml`, but GitHub does not expose repo secrets to workflows triggered by fork pull requests.
- The repo is public; any file committed to it is effectively permanent (git history survives later deletion).

## Goals / Non-Goals

**Goals:**
- One discovery run produces both a cumulative schema and a replayable, anonymized cassette per endpoint.
- Pull request checks never need live credentials.
- Unattended runs can never write to the real Tado account.
- Re-running discovery against unchanged real data never produces a spurious diff.

**Non-Goals:**
- Replacing the JSON-Schema contract with typed models (pydantic/dataclasses) — noted as a possible future evolution, not part of this change.
- Diffing against a third-party/community OpenAPI spec for Tado — no sufficiently authoritative source was identified; out of scope here.
- Changing `libtado/api.py`'s public interface.

## Decisions

### Cassette library: `vcrpy`
`libtado/api.py` uses `requests` directly. `vcrpy` patches `requests` transparently and is the standard choice for this pattern in the Python ecosystem. Alternative considered: hand-rolled JSON fixtures replayed via a custom `requests` mock — rejected, it would duplicate what `vcrpy` already does (matching on method/URL, recording, replaying) for no benefit.

### Anonymization: `Faker`, seeded per field path
Each scrubbed field's fake value is generated by a `Faker` instance seeded from a stable hash of the field's path (e.g. `home.geolocation.latitude`), not from the real value or from wall-clock/random state. This guarantees: (a) the same field always scrubs to the same fake value across runs, so diffs only appear when the real API shape actually changes, and (b) no real value is ever used as input to the fake generator, so there is no reversible mapping back to the original. Alternative considered: static hardcoded placeholders per field — rejected, `Faker` gives type-appropriate values (valid-looking coordinates, emails, etc.) which keeps cassettes realistic for schema/type inference without extra hand-maintained fixtures.

### Schema strategy: cumulative union, not overwrite
The discover script loads the committed schema (if any), feeds it into `genson.SchemaBuilder.add_schema(...)`, then `add_object(...)` with the newly captured (scrubbed) response, and writes the merged result. This makes the schema a superset of every shape ever observed across accounts/device-states, rather than being only as good as the last single sample. Trade-off: a field that Tado actually removes will linger in the schema until manually pruned — accepted, since silently losing a previously-documented field is worse than a stale optional field (see Risks).

### Endpoint scope split: read-only vs. mutating
`tests/api/utils.py`'s `set_cost_simulation` (and any future `set_*` wrapper) is excluded from the endpoint list used by the scheduled trigger. The discover script takes an explicit `--include-mutations` flag (default off); the scheduled workflow never passes it, the manual `workflow_dispatch` workflow exposes it as an opt-in input.

### Drift handling: automated PR via `peter-evans/create-pull-request`
The scheduled job runs discovery, and if `git status` shows changes under `schemas/` or the cassette directory, uses `peter-evans/create-pull-request` to open a PR with those changes on a dedicated branch. No auto-merge step is added. Alternative considered: open a GitHub Issue instead of a PR — rejected per proposal decision, since a PR lets the existing PR test suite (cassette replay) immediately validate whether the new shape still parses correctly, which a plain Issue would not.

### PR tests run on cassettes, not live API
`test.yml` is reactivated to run `tests/api/test_jsonschema.py` (and the parsing-relevant parts of `tests/api/test_api.py`) with `vcrpy` in replay-only mode (`record_mode="none"`), against the committed cassettes. No live secrets are passed to this workflow, which also makes it safe to run on fork PRs.

## Risks / Trade-offs

- **[Risk]** Cumulative schema never drops removed fields → schema slowly overstates what the API actually returns today. **Mitigation**: none automated in this change; a stale field is a documentation nit, not a false negative — accepted for now, revisit if it becomes noisy.
- **[Risk]** Faker's field-path-seeded fakes could, in rare cases, coincidentally collide with a plausible-looking real value pattern, giving false confidence that scrubbing occurred. **Mitigation**: scrubbing operates on a fixed, explicit list of sensitive field paths (not inferred), reviewed at implementation time against every schema in `schemas/`.
- **[Risk]** Weekly automated PRs could still leak personal data if a *new* sensitive field appears that isn't yet in the scrubbing list. **Mitigation**: the discover script fails closed — any field not covered by the schema's known-safe/known-scrubbed classification is scrubbed by a generic type-based Faker fallback rather than passed through raw; a human reviews the PR diff before merge regardless.
- **[Trade-off]** Excluding `set_*` from the schedule means mutating-endpoint schemas can go stale between manual runs. Accepted: safety of the real account outweighs freshness of a rarely-changing write endpoint's schema.

## Migration Plan

1. Add new dev/test dependencies (`jsonschema`, `vcrpy`, `Faker`) to `pyproject.toml`.
2. Build the discover script and scrubbing utility; run it once manually to produce the initial cumulative schemas and cassettes, replacing the current single-sample `schemas/*.json`.
3. Reactivate `tests/api/test_jsonschema.py` against cassette replay; wire it into `test.yml`.
4. Add the scheduled + manual-dispatch discovery workflow with the automated-PR step; retire `check_json_schemas.yml` and `generate_json_schemas.py`.
5. Add the local-dev `Makefile`.

No production/runtime code path is touched, so there is no rollback concern beyond reverting the CI/tooling commits if the new workflow misbehaves.
